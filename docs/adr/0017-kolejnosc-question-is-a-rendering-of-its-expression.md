# The Kolejność question is a rendering of its expression

Every `Kolejność wykonywania działań` Problem carried the same sum twice: a LaTeX `question` hand-written in the generator, and an ASCII `expression` parameter derived from it by `latex_to_expression` for the Deconstruction walkthrough to parse. The two disagreed — the hand-written copy printed a whole-number operand as `\frac{1}{1}`, while the expression module's renderer, which draws the walkthrough's working lines from the very same Problem, printed it as `1` (#318). We decided to invert the direction: the twelve generators in both Chapters author the ASCII, and the question is `render(parse(expression))`, so the LaTeX is derived and `latex_to_expression` is deleted.

**Why this direction and not a patch.** The two strings were already the same function of the same operands, computed twice. Rendering every Problem's `expression` back to LaTeX and comparing it to the hand-written `question` was byte-identical on every one of ~17 000 rolls across all twelve generators — `frac_ord_1`–`frac_ord_6` and `dec_order_1`–`dec_order_6` — with exactly one class of exception, a `\frac{n}{1}` where the renderer wrote a bare integer. There was no second divergence anywhere, in either Chapter. Patching the defect would have left one copy fixed and 38 hand-written operand renders free to reintroduce it.

**Consequence: one formatter, promoted downward.** Three private functions in three modules were separately deciding how to print one value — `_frac` in the Ułamki Zwykłe generator module, `_format_step_answer` in `deconstruction.py` (whose docstring undertook to mirror `_frac` character for character, because the deconstruction contract test pins the final Step's answer to the Problem's own), and `_render_value` in `expression.py`, which already had the correct implementation. Under ADR-0003's first rule the shared thing belongs in the lower module, so `expression.py` exposes it publicly and the other two call it. `expression.py` is where the `Notation` type lives, so the fraction/decimal split stays with the type that names it.

**Constraint this places on future templates.** A power's base must be a fraction or a bracketed sub-expression, never a bare operand. The renderer prints a whole value as a bare integer and restores brackets from the parser's `parenthesized` flag independently of what they contain, so a whole operand under an exponent renders as `(2)^2` rather than the `2^2` a Polish textbook writes. No template can produce that today — every power in the Topic squares either a unit fraction or a bracketed sum — and widening a denominator set cannot introduce it. Widening a *numerator* range over a squared operand would.

**Considered options:** patch the 38 inline operand renders with a shared whole-number helper (rejected — it fixes the copy that has the bug while leaving the duplication that caused it, and nothing then checks the two representations against each other); patch them and add a test asserting the round-trip (rejected — it pays for a tripwire in order to keep a duplication it could delete instead, though it was the honest middle option); convert `topic_130_kolejnosc.py` alone and leave the Ułamki Dziesiętne sibling hand-writing its LaTeX (rejected — the decimal Topic has no defect, since `fmt_dec` already prints a whole value as `1`, but it is built identically, and a rule that holds in one sibling and not the other is the same duplication moved one file over; the round-trip measured clean on every decimal roll, so the conversion is mechanical).

**Consequences.** A template can no longer write LaTeX the grammar does not parse, which is a constraint as much as a benefit: adding a template means extending `backend/expression.py` first. `latex_to_expression` survives only inside `tests/test_kolejnosc_expression.py`, as the test-only inverse that closes its `parse → render → parse` value loop; that inverse can now drift from `render` without a caller noticing, which is the price of keeping the property. The round-trip assertion between `question` and `expression` stops being a check that two independently-built strings agree and becomes a check that there is only one string: it is true by construction against today's code, blind to a renderer fault because both sides run through the same renderer, and still fails the day a template goes back to hand-writing its question — which is the regression worth pinning.
