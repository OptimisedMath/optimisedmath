# Input mode is a closed set on the wire

`current_input_mode` was typed as a free-form `str` in `SessionState` and `SessionResponse` and as `string` in the frontend's mirror, even though CONTEXT.md says there are exactly two input modes and every producer already returns `"radio"` or `"typing"` — so `view.currentInputMode === 'radioo'` compiled, silently selecting the other branch wherever the arena tests the mode. We decided the wire carries a closed two-value set, typed as a literal in both stacks, because input mode is an outcome ADR-0002 assigns to the backend and a closed set enforces the domain's own vocabulary at the boundary that owns it.

**Considered options:** leave it `str`/`string` (rejected — the typo class stays open at both ends, and the client had already invented a third answer of its own for the no-Session case, contradicting Python's default); narrow the TypeScript side only (rejected — a backend typo would still pass validation, cross the wire and fail at render, which puts the check everywhere except where the value is decided); model it as a boolean `is_input_mode` (rejected — the telemetry table already stores that derived form, and collapsing the wire field would lose the name the domain uses and make a third mode unrepresentable rather than merely breaking).

**Consequences:** adding a third input mode is now a breaking wire change rather than a new string, and a stored Session holding an out-of-set value fails validation on read through `to_storage`/`from_storage`. That cost was measured before accepting: all 134 rows in the session store carried `radio` (125) or the typing value (9) when they were counted on 2026-09-17, where the typing value was still spelled `input`, and every assignment site already produced one of the two literals, so no row and no producer needed changing on that day. The client stops inventing its own third value: the no-Session placeholder mirrors Python's `"radio"` default, alongside `max_streak` 3 and `flawless_eligible` true, which nothing renders today but which a future loading state drawn above the arena's early returns would have shown wrongly.

**Amended by #251 — the typing value is `typing`, not `input`.** This ADR was written on 2026-09-17, after #251 had already opened, and it recorded the closed set under the typing value's older spelling. #251 renames that value from `input` to `typing` across the whole repo and renames the glossary's **Input mode** entry to **Typing mode**; the axis keeps the name `input_mode`, and `radio` is untouched. The decision, the rejected alternatives and the reasoning above all stand as written — one of the two values has a different name, not a different meaning — so the literals above read `radio` and `typing`, which is the pair the set closes around. The row count in the consequences is deliberately left in the spelling it was taken in: it is a dated measurement, and respelling it would claim the store held a value it did not yet hold.

#251 lands before #343 closes the set, so the nine rows spelled `input` are respelled by that rename and never meet the closed set as out-of-set values. Nothing is deployed and no Student holds a Session, so if a row is ever found carrying the old spelling it can be dropped or rewritten rather than migrated — the consequence above is a real failure mode for a third mode added later, not a migration this rename owes anyone.
