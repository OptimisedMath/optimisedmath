# Input mode is a closed set on the wire

`current_input_mode` was typed as a free-form `str` in `SessionState` and `SessionResponse` and as `string` in the frontend's mirror, even though CONTEXT.md says there are exactly two input modes and every producer already returns `"radio"` or `"input"` — so `view.currentInputMode === 'radioo'` compiled, silently selecting the other branch wherever the arena tests the mode. We decided the wire carries a closed two-value set, typed as a literal in both stacks, because input mode is an outcome ADR-0002 assigns to the backend and a closed set enforces the domain's own vocabulary at the boundary that owns it.

**Considered options:** leave it `str`/`string` (rejected — the typo class stays open at both ends, and the client had already invented a third answer of its own for the no-Session case, contradicting Python's default); narrow the TypeScript side only (rejected — a backend typo would still pass validation, cross the wire and fail at render, which puts the check everywhere except where the value is decided); model it as a boolean `is_input_mode` (rejected — the telemetry table already stores that derived form, and collapsing the wire field would lose the name the domain uses and make a third mode unrepresentable rather than merely breaking).

**Consequences:** adding a third input mode is now a breaking wire change rather than a new string, and a stored Session holding an out-of-set value fails validation on read through `to_storage`/`from_storage`. That cost was measured before accepting: all 134 rows in the session store carry `radio` (125) or `input` (9), and every assignment site already produces one of the two literals, so no row and no producer needed changing. The client stops inventing its own third value: the no-Session placeholder mirrors Python's `"radio"` default, alongside `max_streak` 3 and `flawless_eligible` true, which nothing renders today but which a future loading state drawn above the arena's early returns would have shown wrongly.
