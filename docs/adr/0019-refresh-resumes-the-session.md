# A refresh resumes the Session; a Stale one does not

A browser refresh started a brand-new Session: the frontend called session start on every mount, never sending the id it had stored, and the backend always constructed a fresh `SessionState`. So a refresh, a tab reopen, or a phone dropping and restoring the tab reset Streak, Flawless, the deconstructed set and — after [ADR-0014](0014-deconstruction-trigger-counts-per-session.md) put the Misconception hit counts on the Session — the evidence a Deconstruction fires on. **Decision:** a page load **resumes** the Session whose id the browser holds, reviving everything the Session owns and re-reading everything the profile owns. A Session ends at logout, or by going **Stale** after 12 hours untouched, measured from its last Submission or Navigation.

**Why a refresh was the wrong boundary.** A refresh is not a decision to stop playing. The Student cannot perceive which Session-scoped fields survive it, but they can perceive their stars vanishing — so any rule that revived the Misconception counts while dropping Streak would be a distinction only the code could see. Resuming everything is also what the storage layer already did: the whole `SessionState` is written to the sessions table on every Submission, and the lookup behind every gameplay endpoint already falls back to it. Reviving a subset would have meant *adding* a filter.

**Considered options:** revive the Misconception state only, keeping Streak and Flawless Session-fresh — rejected, it preserves ADR-0006's wording at the cost of a rule nobody can explain from the outside, and leaves the headline complaint (a refresh wipes the meter) unfixed. Logout as the sole boundary — rejected, it makes "a Misconception is deconstructable again in a later session" depend on the Student remembering to log out. A calendar-day cut — rejected, a 22:00→00:30 sitting would be split in two. Enforcing staleness on every request rather than at resume — rejected, it would pull a Streak out from under a Student still sitting at the keyboard, with no refresh to explain it; the cut exists to re-arm Misconceptions on a new day, not to police an idle tab.

**Consequences.** Streak and Flawless now survive a page load. [ADR-0006](0006-profile-owns-selected-not-streak-or-flawless.md)'s "every new Session starts Streak at 0" is unchanged and still true — a Resume is not a new Session — but it now reaches far fewer situations than it did when every page load was one.

A Session is now long-lived enough for the Curriculum to change underneath it, so a Resume re-runs the two healing steps a fresh start runs — seeding a Frontier record for every Chapter, and clamping the Selected level to the Topic's current max. Without the first, a Chapter added between two page loads reintroduces the `KeyError` of #214 through a door it never had.

A Session row also carries its own copy of XP and the Frontier, which [ADR-0006](0006-profile-owns-selected-not-streak-or-flawless.md) says the profile owns. A Resume re-reads both from the profile rather than trusting the snapshot, so a second device's progress is not clobbered by a stale figure in a tab refreshed hours later. Selected is deliberately *not* re-read: ADR-0006 seeds it from the profile at Session **start**, and re-reading it would teleport a resumed tab to wherever another device last navigated.

Three paths now delete a Session row that can no longer be reached: logout, login (which ends whatever was stored before minting its replacement), and a resume that declines a Stale Session. Logout's call is deliberately fire-and-forget from a `<Link>`, so a lost race leaves an unreachable row — the same outcome as not deleting at all. Rows from a tab simply closed and never reopened are deleted by none of the three and accumulate.

The error screen's **Spróbuj ponownie** used to escape a wedged Session by accident, because its reload minted a new one. It no longer does. That escape was never designed; the deliberate ones — **Wyloguj**, and the progress reset behind its confirmation — remain.
